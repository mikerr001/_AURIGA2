The ecosystem

Useful tools, designed around real life.

Instead of one giant interface that tries to do everything, Auriga is being developed as a set of focused tools. Each tool should make its state clear and avoid pretending it knows something it cannot verify.

Design principles

Trust is part of the interface.

Assistive software must communicate uncertainty clearly. A polished screen is not a substitute for a reliable sensor pipeline.

01 / PRIVACY

Prefer local processing

The product direction prioritises on-device processing and avoids requiring an account or cloud service for core features wherever practical.

02 / HONESTY

Say when the system is unsure

If a model or scale estimate is unavailable, the interface should disclose that state instead of inventing a distance or a confident warning.

03 / ACCESS

Make the controls usable

Clear focus states, large touch targets, concise language, reduced motion, and screen-reader semantics are baseline requirements—not extras.

Clear answers, no overpromises.

Does Auriga require the cloud?

The goal is local-first operation. Some optional website features and model downloads may need an internet connection; individual capabilities vary by build.

Is the Android app the same as the web demo?

No. The Android app is a native camera application. The web demo is a separate browser prototype and should never be presented as the native detector.

Can I install the latest APK?

Open the Android CI page to see the latest build status and available artifacts. An APK is only ready when the workflow completes successfully and uploads one.

How can I report a problem?

Use the GitHub issue tracker or email drakosanctis@gmail.com. Include your device model and the steps that reproduce the issue, but never share passwords or private keys.
